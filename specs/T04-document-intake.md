# T04 — Document Intake and Preparation

Status: the resource layer and collection actor are implemented and verified locally with controlled Telegram substitutes; see the [T04 progress report](../docs/testing/T04_PROGRESS_REPORT.md). No real Telegram request or sealed benchmark was performed; Telegram delivery-path verification remains part of the joint E2E. Updated: 2026-09-28; specification revised after the independent review (Telegram photo path, admission control, album limits, lazy rendering).

## Goal and Basis

Convert a single file, Telegram album, or Several pages set into one ordered temporary document without losing pages or mixing owners.

Basis: [PRODUCT_SPEC](../docs/requirements/PRODUCT_SPEC.md), REQ-002/003/011/012/015/019/020/025/026; [USER_FLOWS](../docs/requirements/USER_FLOWS.md); [STATE_MACHINE](../docs/architecture/STATE_MACHINE.md); [DATA_MODEL](../docs/architecture/DATA_MODEL.md).

## Scope and Dependencies

- Depends on [T02](T02-application-foundation.md), [T03](T03-access-and-profiles.md), [CONTRACTS](../docs/architecture/CONTRACTS.md), and [OPERATIONS](../docs/operations/OPERATIONS.md); uses the page-preparation module of the T01b recognition core.
- Authorized private-chat user only; one unfinished document per user. A file is not downloaded before login and the pre-download admission check; a new separate document does not silently displace the active one.
- Standard Bot API, 20 MB per file. No fixed page or file cap and no hidden first-pages-only limit; a set that cannot finish within the processing budget is refused explicitly (ED-002).
- A single image/PDF starts automatically; a Several pages set is collected until Process; Process with no files reports that no document is present.
- Collection/clarification period: 15 minutes of inactivity, configurable. The album completion window and the definition of activity are specified in STATE_MACHINE and OPERATIONS.

## Implementation Result

1. A Submission is created with an owner, job ID/generation, admission time, and stable file/page IDs; page order is preserved within PDFs, and albums are sorted by message ID.
2. A Telegram photo is taken at its largest available size, and the job records that it came through the compressed photo path; files keep their original bytes. A Telegram album holds at most 10 items and groups files only with files, so larger or mixed photo/PDF sets use Several pages.
3. Temporary paths are generated by the application within the job directory; the original name, MIME, or extension is not treated as a trusted path/proof of format.
4. Downloads pass through the global download limiter. Download availability and actual format are checked; pages are counted at intake for admission. Images are decoded under the configured pixel limit, and PDFs are opened with a safe parser in a child process; contents are not executed and external links are not opened.
5. A corrupt/protected PDF, unsupported format, oversized decoded image, and download error receive an explicit English-language outcome. The document password is not guessed.
6. PDF pages are rendered lazily per batch within memory limits, without loading all rasters at once, and deleted after use. The full document is not truncated to fit the model context.
7. Preprocessing does not overwrite the original. Orientation/scale and source association remain traceable within the temporary job.
8. Redelivery of a Telegram update does not duplicate a file. Messages from different users and media groups are not placed in the same set.
9. A late fragment of the same album before delivery starts invalidates the previous pass: cancel/terminate the worker, complete the collection, and run a new pass without the old response. After delivery has started, the result is marked incomplete and Several pages is offered; the fragment does not silently become a new document.

## Acceptance and Checks

- PNG, JPEG, single-page and multi-page PDFs, albums, and mixed image/PDF sets through Several pages produce the expected order, page count, and source of every page.
- The same image through the photo path and the file path is accepted; the photo path uses the largest size and is recorded as compressed.
- Process with no files, Cancel, repeated update, late album, a second document file while a job is active, and another user's callback are checked.
- False extension/MIME, incorrect path/name, corrupt PDF, password, oversized decoded image, download error, and Bot API limit are checked; the parser does not execute the document.
- A set that cannot finish within the budget at the lower-bound per-page time is refused before recognition with an explanation; a full admission pool answers Busy before download.
- A large multi-page input either processes all pages in batches or ends with an explicit error, without a successful incomplete result.
- 15 minutes of inactivity lead to expiry and cleanup; late files/buttons do not revive an expired job. The timeout configuration is checked.
- Preparation error, cancellation, and restart clean up originals/derived data; contents are absent from logs/backup. A running parser/worker does not read a file that has already been deleted.

## Completion Conditions and Exclusions

Completion is confirmed by completed scenarios and actual application check commands. Album window, quotas, admission, parser isolation, and cancellation are defined in STATE_MACHINE, OPERATIONS, and USER_FLOWS. A resource error is not reported as a missing field.

Recognition, a new UI outside Telegram, document archive, a separate OCR stage, persistent queue, bypassing 20 MB, or a fixed page or file cap are out of scope.
