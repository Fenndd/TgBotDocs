# Security and Data Lifecycle

Status: first-version requirements and test plan, 2026-09-27. Product security has not yet been confirmed through testing.

## Trust Boundary

REQ-008/014/020 define temporary retention and local processing; REQ-010/018/029 define access and personal isolation. Model processing runs on the current PC; Telegram is an external transport. Local inference does not promise that the file/response has no copies in Telegram.

| Data | Permitted handling |
| --- | --- |
| Originals, pages, intermediate text, candidates, evidence, results | RAM and isolated temporary directory; deletion on every completion, cancellation, error, TTL, and startup after a crash |
| Personal profiles and versions, necessary owner data | PostgreSQL; only the owner can view/change/use |
| Authorization and conversations | RAM until logout/restart; password from local configuration |
| Logs | Stage/error code, random job ID, duration/resources, versions; no content, passwords, tokens, file IDs, original filenames, or full Telegram updates |
| Backup | Only permitted persistent settings/DB; temporary content is excluded |
| Telegram copies | External lifecycle; the application does not promise to delete all copies |

Initial technical durations/quotas are in [OPERATIONS](../operations/OPERATIONS.md). Temporary directories are not inside automatically synchronized or backed-up directories. A profile does not automatically receive example values from a document.

## Access Protection

Private chats, the correct shared password, and owner ID are checked before upload/processing. A callback contains a reference to the current object, but does not grant authority by itself: owner, state, and job generation are checked. Other users' profile IDs do not reveal whether those profiles exist.

Brute-force attempts are limited; the entered password is not logged or repeated by the bot. Deletion from Telegram history can be attempted, but is not considered a guarantee that external copies are deleted. Secrets and actual documents are not put in Git.

## Untrusted Inputs

The format is checked by content, not only by extension; the file path is generated by the application. PDFs do not execute JavaScript, embedded programs, links, or commands. A password-protected/damaged PDF receives a clear refusal.

Document text and settings do not give the model tools/code execution. They cannot change the inference endpoint, access, retention, or system rules. The model returns only data under the contract; extra text does not pass directly into Telegram. Output is escaped so recognized characters do not turn into formatting commands or unsolicited links.

## Cleanup and Diagnostics

Cancellation/timeout invalidate late responses, stop active readers, and delete files/derived data. A deletion failure is not hidden: new uploads are blocked until a safe state is reached. Startup checks for leftovers before long polling. A powered-off PC does not run timers; cleanup of crash leftovers is checked at the next startup.

The runtime does not write prompts/completions, HTTP bodies, or images to debug traces. When preparing the delivery, its logs and temporary directories are checked, along with the OS dump/paging configuration. Ordinary file deletion does not promise physical erasure from the SSD, memory, or all system traces.

[Resilience tests](../../specs/T07-acceptance-and-resilience.md) include success, error, cancellation, expiry, crash, deletion failure, cross-user access, and log/backup contents. The plan is not a legal opinion, document authenticity audit, or promise of absolute protection.
