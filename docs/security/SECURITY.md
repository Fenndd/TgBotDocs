# Security and Data Lifecycle

Status: first-version requirements and test plan, 2026-09-27; revised after the independent review (access hardening, result rendering, runtime memory, staged cleanup failure). Product security has not yet been confirmed through testing.

## Trust Boundary

REQ-008/014/020 define temporary retention and local processing; REQ-010/018/029 define access and personal isolation. Model processing runs on the self-hosted machine that runs the bot — the current PC during development (S-11-A1); Telegram is an external transport. Local inference does not promise that the file/response has no copies in Telegram.

| Data | Permitted handling |
| --- | --- |
| Originals, pages, intermediate text, candidates, verification-signal values, evidence, results | RAM and isolated temporary directory; pages rendered per batch; deletion on every completion, cancellation, error, TTL, and startup after a crash |
| Personal profiles (current version only), necessary owner data | PostgreSQL; only the owner can view/change/use |
| Authorization and conversations | RAM until logout/restart; password from local configuration; the password message is deleted after the check |
| Model runtime memory | Host-memory prompt cache disabled; the single slot's cache is overwritten by the next call |
| Logs | Stage/error code, random job ID, duration/resources, versions; no content, passwords, tokens, file IDs, original filenames, or full Telegram updates |
| Operator alerts | Event code, time, and random job ID only; sent only to configured operator IDs |
| Backup | Only permitted persistent settings/DB; temporary content is excluded |
| Telegram copies | External lifecycle; the application does not promise to delete all copies |

Initial technical durations/quotas are in [OPERATIONS](../operations/OPERATIONS.md). Temporary directories are not inside automatically synchronized, indexed, or backed-up directories. A profile does not automatically receive example values from a document.

## Access Protection

Private chats, the correct shared password, and owner ID are checked before upload/processing. The shared password stays the access model (S-01, REQ-010), with these safeguards (ED-009): constant-time comparison; deletion of the message that contains the password; per-user limits on failed attempts and an operator alert on a global surge; group joining disabled in BotFather at delivery, in addition to the private-chat check. A callback contains a reference to the current object and a per-process nonce, but does not grant authority by itself: owner, state, and job generation are checked. Other users' profile IDs do not reveal whether those profiles exist.

The entered password is not logged or repeated by the bot. Deletion from Telegram history can be attempted, but is not considered a guarantee that external copies are deleted. Secrets and actual documents are not put in Git; the real configuration file lives outside the source tree that development assistants read. The llama-server API listens on loopback and requires an API key.

## Untrusted Inputs

The format is checked by content, not only by extension; the file path is generated by the application. PDFs do not execute JavaScript, embedded programs, links, or commands. A password-protected/damaged PDF receives a clear refusal. Decoded images above a configured pixel limit are refused as unsafe (initially the Pillow decompression-bomb threshold), and PDF pages are rendered at the configured resolution only.

Document text and settings do not give the model tools/code execution. They cannot change the inference endpoint, access, retention, or system rules. The model returns only data under the contract; extra text does not pass directly into Telegram. Values are rendered as `code` entities without a parse mode, and link previews are disabled, so recognized characters do not turn into formatting, links, mentions, or commands ([CONTRACTS](../architecture/CONTRACTS.md)).

## Cleanup and Diagnostics

Cancellation/timeout invalidate late responses, stop active readers, and delete files/derived data. A deletion failure is not hidden: after retries with backoff, intake closes for everyone, the operator is alerted, and intake reopens only when the leftovers are gone (ED-006). Child processes end with the bot, and startup terminates leftovers of the previous run before checking for files. Startup checks for leftovers before long polling. Antivirus real-time scanning is not disabled for the temporary directory; transient file locks are handled by the deletion retries. A powered-off PC does not run timers; cleanup of crash leftovers is checked at the next startup.

The runtime does not write prompts/completions, HTTP bodies, or images to debug traces, and its host-memory prompt cache is disabled (launch profile in OPERATIONS). When preparing the delivery, its logs and temporary directories are checked, along with the OS dump/paging configuration. Ordinary file deletion does not promise physical erasure from the SSD, memory, or all system traces.

[Resilience tests](../../specs/T07-acceptance-and-resilience.md) include success, error, cancellation, expiry, crash, deletion failure, stale updates, cross-user access, and log/backup contents. The plan is not a legal opinion, document authenticity audit, or promise of absolute protection.
